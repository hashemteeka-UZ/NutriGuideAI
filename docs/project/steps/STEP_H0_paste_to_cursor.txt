## C. The optimizer `app/services/optimizer.py` (#109, #110, #112-#115)
Public API:

```python
PLANNER_VERSION: Final = "cpsat_v1"
GENERATED_BY: Final = "cpsat"

@dataclass(frozen=True)
class OptimizedDay:
    plan: DayPlan               # planner.DayPlan with planner_version="cpsat_v1"
    solver_status: str          # "OPTIMAL" or "FEASIBLE"
    kcal_relaxed: bool          # True when phase 2 (soft energy) was needed
    objective: int
    solve_seconds: float        # wall time of all solve calls (reported only, never asserted)

def optimize_day(
    meals: Sequence[MealFacts],
    preferences: UserPreferences,
    limits: ResolvedLimits,
    target: PlanTarget,
    plan_date: date,
    nutrient_codes: Sequence[str],
    excluded_meal_ids: frozenset[int] = frozenset(),
) -> OptimizedDay: ...
```

`optimize_day` does NOT call `apply_general_limits`; the caller passes the limits it wants (H.1 will pass the merged ones). Reuse from planner: `MAIN_SLOTS`, `SLOT_ENERGY_SHARE`, `SNACK_ENERGY_SHARE`, `MULTIPLIERS`, `MAX_SNACKS`, `KCAL_TOLERANCE`, `PlanItem`, `DayPlan`, `PlanTarget`, `NoFeasiblePlanError`, `reason_codes`, `slot_target_kcal`, `unmet_minimums`, `PROTEIN_NUTRIENT`. Do not duplicate them.

### C.1 Candidates (#109, #110)
- Positions: `breakfast`, `lunch`, `dinner`, `snack_1`, `snack_2` (`MAX_SNACKS` = 2 snack positions, both use slot `MealSlot.SNACK` for Layer 1 and in the output).
- For every position, every meal (sorted by `sort_key`) and every step in `MULTIPLIERS`, create a boolean `x[position, meal, step]` only when ALL hold:
  - `evaluate_meal(meal, preferences, slot, limits, step).eligible` (Layer 1 is never re-modelled);
  - `meal.meal_id not in excluded_meal_ids` (previous day, #88 criterion 4);
  - energy and every nutrient in `limits.max_per_day` and `limits.min_per_day` are known for the meal (`amount(...)` is not None). A missing amount is never treated as zero (§9.8, same meaning as greedy).
- If a main position has no candidate, raise `NoFeasiblePlanError(slot, reasons, candidates)` with the same counting idea as greedy (count per rule how many (meal, step) pairs were removed; use the Layer 1 exclusion codes plus `PREVIOUS_DAY` and `UNKNOWN_AMOUNT:<nutrient>`). Define these two rule names as constants in optimizer.py.

### C.2 Hard constraints (#110)
- Each main position: exactly one selected variable.
- Each snack position: at most one; `sum(snack_2) <= sum(snack_1)` (symmetry breaking).
- Each meal at most once in the day over all positions and steps.
- Each non-null `variant_group` at most once in the day.
- Every `max_per_day` nutrient: day total <= limit.
- Every `min_per_day` nutrient: day total >= minimum (hard, #81).
- Every LIMIT tag with a non-null weekly number: sum of steps of selected meals carrying the tag <= weekly number (within the day, #89). Model steps as integers in half-servings (step × 2).
- Phase 1 only: day kcal within [target × (1 - KCAL_TOLERANCE), target × (1 + KCAL_TOLERANCE)].

### C.3 Integer scaling (#114)
- `SCALE: Final = 1000`. Coefficients of upper-bound constraints use ceil(amount × SCALE) and the bound uses floor(limit × SCALE); lower-bound constraints use floor for coefficients and ceil for the bound. Use `Decimal` with explicit rounding, never float, when building coefficients.
- After solving, recompute every hard constraint with exact `Decimal` amounts on the chosen items (a private `_verify(...)`), including the kcal band in phase 1. Any failure raises `AssertionError` with the rule name (a programming error, never hidden).

### C.4 Objective (#113)
All terms in integer "kcal-equivalent × 10" units (use the scaled totals and divide consistently, or scale weights; document the unit in a comment). Minimize:
- `W_KCAL = 3` × |day kcal - target.kcal|
- `W_MACRO = 1` × (|protein - target.protein_g| × 4 + |carbohydrate - target.carb_g| × 4 + |total_fat - target.fat_g| × 9)  (use the nutrient codes the planner and targets use; check `targets.py`/`nutrients` codes, do not guess)
- `W_FIBER = 1` × max(0, target.fiber_g - fiber) × 4
- `W_SLOT = 1` × sum over main slots of |slot kcal - SLOT_ENERGY_SHARE[slot] × target.kcal|
- minus `LIKED_BONUS = 10` per selected item whose `ingredient_ids` intersect `preferences.liked_ingredient_ids` (Layer 2).
- Phase 2 only: `W_KCAL_RELAXED = 50` replaces `W_KCAL`.
Absolute values via auxiliary IntVars with two inequalities each (standard linearisation). Macro nutrients that are unknown for a candidate: exclude that candidate (add those codes to the "must be known" list of C.1) so totals are always exact.

### C.5 Phases (#112) and determinism (#115)
- Phase 1 (hard kcal band). If the status is INFEASIBLE, phase 2: same model without the kcal band, `kcal_relaxed=True`. If phase 2 is INFEASIBLE, raise `NoFeasiblePlanError` for slot `"day"` with reasons naming the binding rule family where known (at least `{"INFEASIBLE": 1}`); no limit is ever relaxed, no slot dropped.
- Accept `OPTIMAL` or `FEASIBLE`; anything else (UNKNOWN, MODEL_INVALID) raises `PlanError` with the status name.
- Solver parameters: `num_workers = 1`, `random_seed = 0`, `max_deterministic_time = 10.0`, `log_search_progress = False`. Create variables in a fixed order (position order, then `sort_key`, then step).
- Output: items in position order breakfast, lunch, dinner, snack_1, snack_2 (unused snacks omitted), each a `PlanItem` built exactly like `plan_day` builds it (same `nutrients` dict rule and `reason_codes(meal, step, slot_target_kcal(slot, target.kcal, snack_count), limits, preferences)`). `totals`, `kcal_within_10pct` (computed from the exact Decimal kcal, not from the phase) and `unmet_minimums` computed as in `plan_day`; `unmet_minimums` must be empty by construction (assert it in `_verify`).

## D. Tests `tests/services/test_optimizer.py` (pure)
Build `MealFacts` by hand with a small helper (tags must include the `SLOT_OCCASION` tag of each slot the meal may fill; `is_active=True`, `is_nutritionally_complete=True`; per_serving with energy, protein, carbohydrate, total_fat, fiber, sodium, saturated_fat and sugars using the real nutrient codes). Build `ResolvedLimits` and `PlanTarget` by hand. Cover at least:
1. Healthy case: 3 main items, kcal within ±10%, `solver_status` OPTIMAL, `planner_version == "cpsat_v1"`.
2. A case where greedy-style early choice would fail but the optimizer succeeds: construct meals so the kcal-closest breakfast uses most of a sodium budget and leaves no valid dinner; assert `optimize_day` returns a plan within the sodium limit. (Also call `planner.plan_day` on the same input and assert it raises `NoFeasiblePlanError` or misses the kcal band; keep the assertion to what actually happens and comment why.)
3. Every hard rule: max_per_day, min_per_day met (fiber minimum reached when a combination exists), meal used once, variant_group once, LIMIT tag servings, Layer 1 exclusion (allergen / AVOID tag) never selected.
4. `excluded_meal_ids` are never selected.
5. Unknown amount: a meal missing sodium while sodium has a max_per_day is never selected.
6. Phase 2: a catalog that cannot reach ±10% returns `kcal_relaxed=True`, `kcal_within_10pct=False`, hard limits still met.
7. Infeasible minimum (no combination reaches it): raises `NoFeasiblePlanError`.
8. Empty main position (no breakfast candidates): raises `NoFeasiblePlanError` with slot `breakfast` and the reason counts.
9. Determinism: two calls on the same input give equal `plan` objects; shuffling the input meal order gives the same plan.
10. Liked-ingredient bonus breaks a tie between two otherwise identical meals.
11. `snack_2` never used without `snack_1`.
12. Decimal verification: a hand-checked case where the exact total equals the limit is accepted.
