## 2. Package `app/pipeline/` (Decision #92)
Modules (names may vary, responsibilities may not):
- `files.py` — pydantic models and readers for the catalog directory (default `backend/data/catalog/`, overridable with `--data-dir`):
  - `reference_seed.yaml`: the same schema as `app.seed.f1_files.ReferenceSeed` (reuse it), plus a new list `uncertain_keywords` (§31.6: matches go to quarantine, not exclusion).
  - `ingredients.yaml`: `dataset_version`, then `ingredients:` entries with `code` (`^[A-Z][A-Z0-9_]*$`, unique), `name_en`, `name_ar`, `aliases_en: []`, `aliases_ar: []`, `food: {source: SR_LEGACY | MANUAL, code: <NDB number or manual code>}`, `state` (`raw` / `cooked` / `as_purchased`), `allergens` (allergen **codes**), `ingredient_tags` (tag codes), `review_status` (`PENDING` / `APPROVED`).
  - `manual_foods.yaml` (optional file): foods absent from USDA (#93 step 4): `code`, `description`, `category` (FDC category code present in `categories_ar`), `state`, `source_reference` (non-empty, full citation), `nutrients: {<nutrient code>: <amount per 100 g>}`.
  - `meals/*.yaml` (any number of batch files, read in file-name order): file header `dataset_version`, `source`, `source_license`, `default_lang`; each meal like `SliceMeal` but ingredients reference `code` (ingredient code) instead of `ndb_number`, `ref_external` must start with `NG-`, and a new field `yield_factor_kind: PUBLISHED | TEAM_ESTIMATE` (required when `weight_method = YIELD_FACTOR`, forbidden otherwise). Optional `cross_check: {status: PASS | FAIL_REVIEWED, note: <text>}` (filled in G.5).
  - `sources/source_manifest.yaml` + `sources/sr_legacy_subset.csv` + `sources/fndds_ingredient_subset.csv`: written by the extractor (§3), read by the build.
  - Authoring errors (schema violations, unknown codes, duplicate `ref_external` or ingredient codes, a subset file whose SHA-256 differs from the manifest) fail the whole run with every error listed. They are bugs in the files, not data-quality outcomes.
- `extract.py` — CLI `uv run python -m app.pipeline.extract [--profile-only]` (§3).
- `profile.py` — `pandera` schemas for the raw tables used: SR `food.csv`, `food_nutrient.csv`, `nutrient.csv`; FNDDS `Ingredient Nutrient Values`, `FNDDS Nutrient Values`, `Portions and Weights`, `Foods and Beverages`. Check columns, dtypes, non-null keys, non-negative amounts, key uniqueness; collect all errors lazily.
- `gates.py` — record-level gates (§31.3). Reuse the F.1 gate functions where they fit (energy consistency G2, weight method G6, percent-energy limits G7, optional ingredients G8, variant groups G9). New gates:
  - **G10** manual threshold tags: `high_sodium` / `high_sugar` may not appear in `ingredient_tags` or a meal's manual tags (they are derived per meal, §10.5, #74).
  - **G11** yield-factor kind: `PUBLISHED` requires a non-empty `yield_factor_source`.
  - **G12** manual foods carry every mandatory nutrient and a non-empty `source_reference`.
- `classify.py` — one outcome per record, with a reason code:
  - **excluded**: an excluded keyword (whole word, case-insensitive) in a food description, ingredient name or alias → `non_permissible_ingredient`; a meal using an excluded ingredient → `uses_excluded_ingredient`.
  - **quarantine**: `uncertain_keywords` match → `ingredient_status_uncertain`; a mandatory nutrient still missing after the fill of §4 → `missing_mandatory_nutrient`; energy inconsistent (G2) → `energy_inconsistent`; a meal using a quarantined ingredient → `uses_quarantined_ingredient`; a meal with no `reviewed_by` → `not_reviewed` (catalog rule: every recipe is reviewed before loading, §31.4, #95); a meal failing G6/G8/G10/G11 → the gate name.
  - **accepted**: everything else. Only accepted records are loaded.
- `load.py` — idempotent single-transaction load of accepted records (§5).
- `report.py` — writes `reports/run_report.md` and `reports/records.csv` (§6).
- `build.py` — CLI `uv run python -m app.pipeline.build [--data-dir PATH] [--load]`: read → validate → fill → gate → classify → report; with `--load` also writes the database. Exit code non-zero on authoring errors.

## 3. Extraction (`app.pipeline.extract`)

- Run the `pandera` profiles on every raw table and write `reports/raw_profile.md`: rows, columns, null counts of key columns, schema errors (expected: none), and duplicate keys.
- **#93 feasibility (always runs, also with `--profile-only`)**: in the same report, for the whole SR Legacy food set, count foods missing at least one mandatory nutrient (use the nutrient numbers in `reference_seed.yaml` → `nutrients[].source_code`), and how many of those gaps the FNDDS *Ingredient Nutrient Values* file fills for the same code (FNDDS ingredient code = SR NDB number as an integer). Show the per-nutrient table and these two cases from F.1 finding F-03: NDB 17013 (lamb) and 20028 (dry couscous) — which nutrients SR lacks and the FNDDS values for them. Also report how many FNDDS values for nutrients SR *does* publish differ by more than 5% (agreement check).
- Without `--profile-only`: read `ingredients.yaml`, and write `sources/sr_legacy_subset.csv` (same columns as `data/f1_slice/fdc_sr_legacy_subset.csv`, rows only for the referenced SR codes, absent values never written) and `sources/fndds_ingredient_subset.csv` (`ndb_number,nutrient_nbr,amount_per_100g` for the same codes and the seed's nutrients).
- `--profile-only` must work when `ingredients.yaml` does not exist yet (the case in this pass).

## 4. Nutrient source order (#93)
For each SR food: values come from the SR subset. For each nutrient of the seed missing in SR, take the FNDDS ingredient value for the same code if present (a published FNDDS 0 counts); record every fill as `(ndb, nutrient code, value, "FNDDS 2021-2023 Ingredient Nutrient Values")` in the run report and append a sentence to `foods.source_reference`, e.g. `USDA FDC SR Legacy (April 2018), NDB 17013; sugars from FNDDS 2021-2023 Ingredient Nutrient Values`. Still missing → quarantine `missing_mandatory_nutrient` (an optional nutrient may stay absent). `MANUAL` foods use their file values only (`foods.external_source = 'MANUAL'`, `external_code = code`, `fdc_id` NULL). Run G1 and G2 on the filled values.

## 5. Loading
- Reference rows from `reference_seed.yaml` upsert by their natural keys exactly as `f1_loader` does (categories by `name_en`, cuisines/allergens/tags/conditions/nutrients by `code`, limits by their unique key, restrictions by `(condition, tag)` with `source_reference`).
- Foods upsert by `(external_source, external_code)` (`FDC` for SR foods, as in F.1); `food_nutrients` synced to exactly the filled values. Ingredients upsert by `code` with `default_food_id`, `review_status`, allergens, tags; aliases with `source = <ingredients dataset_version>` replaced to match the file.
- Meals upsert by `(source, ref_external)`; `dataset_version` from the batch header; `quality_tier` **computed**, never read from the file (#96): `GOLD` when reviewed and (`WEIGHED`, or `SUM_OF_INGREDIENTS`, or `YIELD_FACTOR` with `PUBLISHED`) and `cross_check.status` is not `FAIL_REVIEWED`; otherwise `SILVER`. `is_verified = reviewed_by is not null`. Meal ingredients reference `ingredient_id` and the ingredient's default `food_id`.
- Deactivation (#79): active meals with the catalog's `dataset_version` that are not accepted in this run (removed, quarantined or excluded) become `is_active = false`; never deleted. Meals of any other `dataset_version` (e.g. the F.1 slice) are never touched.
- After loading, run `compute_meal_nutrients` then `recompute_meal_derived` for every accepted meal, in the same transaction.

## 6. Reports
