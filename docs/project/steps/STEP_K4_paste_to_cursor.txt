## 2. Plan cache (#255)
New drift tables (schemaVersion 3, migration 2 -> 3 with the generated migration test):
- `plans`: `plan_date` PK (YYYY-MM-DD), `plan_id`, `algorithm_version`, `created_at`, target (`kcal`, `protein_g`, `carb_g`, `fat_g`, `fiber_g`), totals (all `NutrientTotals` fields nullable), `kcal_within_10pct`, stats (`solver_status`, `kcal_relaxed`, `solve_seconds`, `candidate_meals`, all nullable), `fetched_at`.
- `plan_items`: `plan_item_id` PK, `plan_date` FK cascade, `position`, `slot`, `meal_id`, `meal_name` (the server name at fetch time, used only if the catalog has no row), `servings_multiplier`, `grams`, `kcal`, `protein_g`, `carb_g`, `fat_g`, `reason_codes` (JSON text), `was_swapped`, `logged`.
- `plan_unmet_minimums`: (`plan_date`, `nutrient`) PK, `minimum`, `total`.
- `meal_windows`: (`window_date`, `slot`) PK, `start`, `end` (HH:MM), from `GET /days/{date}`.
- `day_summaries`: `summary_date` PK, the adherence fields needed by Today (`target_kcal`, totals kcal/protein/carb/fat, `plan_items_total`, `plan_items_consumed`, `status`), water `total_ml`, `goal_ml`, `requires_clinician`, `fetched_at`.
- All five are personal: add them to the logout / account-switch wipe from K.3.
- `PlanRepository.refresh()`: `GET /plans?from=<local yesterday>&to=<local today + 13>` and replace that whole date range in ONE transaction (dates with no plan in the response are deleted). Triggers: app start with a session, app resume (`AppLifecycleState.resumed`, at most once per 5 minutes), after generation, after a swap, pull-to-refresh on Today and Plan. One request in flight, shared.
- `TodayRepository.refreshDay(date)`: `GET /days/{date}` -> upsert `meal_windows`, `day_summaries` and the plan of that day. Called for today on the same triggers.
- Screens read only from drift streams (`watch`), so they update when a refresh lands and work offline.
- Dates are the device local date (`DateTime.now()`), formatted YYYY-MM-DD.

## 3. Week generation and showcase screen (#253, #254)
- Entry points: (a) the onboarding result button «ابنِ خطتي الأولى» (eligible users only) now opens the showcase and then `/today`; (b) Today with no plan for today shows a card «لم تُبنَ خطة اليوم بعد» with «ابنِ خطة الأسبوع»; (c) the Plan tab refresh icon «إعادة البناء» with a confirm dialog «سنبني أيام الأسبوع من جديد. الأيام التي سجلت فيها وجبة تبقى كما هي.».
- `WeekGenerator` (domain + data, unit-tested with a fake API): dates = local today .. today + 6. Skip a date whose cached plan has any item with `logged == true`. For each date in order: `POST /plans/days {date}`. On 201 store that day immediately (so the UI can show it). On 503 `PLANNER_BUSY`: wait `Retry-After` seconds (default 5 if missing, cap 30), retry the same date, at most 3 tries, then stop. On 503 `PLANNER_TIMEOUT`: stop, message «تعذر بناء الخطة الآن، حاول مرة أخرى بعد قليل». On 429 `RATE_LIMITED`: stop, message with the seconds from `Retry-After`. On `NOT_ELIGIBLE`: stop, general mode. On `NO_TARGET`, `PROFILE_NOT_FOUND`: stop, generic message and route to onboarding re-check. On `NO_FEASIBLE_PLAN` or `CONDITION_CONFLICT` for one date: record that date as failed, continue with the next date. Network failure: stop, keep built days, message with retry. Never loop on errors. Exposes a stream of progress events (date started, date done with `DayPlanOut`, date failed with code, finished).
- After the loop: `PlanRepository.refresh()`.
- Showcase screen (dark `.gen` style, like `genSkeleton`): header «نبني خطتك الآن» with «تخطي» (skip keeps generating in the background and opens `/today`; the generator lives in a provider, not in the widget). Four steps that light up in order:
  1. «نحسب احتياجك»: the daily kcal from the cached targets (K.2 `GET /me/targets`) counting up, with chips from server fields only: «BMR …», «× …» (tdee/bmr, 3 decimals), «TDEE …», and «− …» or «+ …» (|kcal − tdee|) unless MAINTAIN.
  2. «نستبعد ما لا يناسبك»: the number of meals in the local catalog (catalog_meta.meal_count) counting down to `stats.candidate_meals` of the first returned day, with filter chips derived from the user's data only: «تجنب <allergen name>» for each `user_allergens` code, «ملح أقل» if HYPERTENSION or HEART_DISEASE, «سكريات أقل» if DIABETES_T2, «بدون ما لا تحبه» if any DISLIKE exists. Read conditions from `GET /me/profile` (already fetched in K.3 sync; keep the codes in memory, do not add a table).
  3. «المحسّن يبحث عن أفضل تركيبة»: day 1 in detail: four slot reels that settle on the real meals of day 1 (names from the catalog), and check rows «السعرات ضمن ±10%» (`kcal_within_10pct`), «البروتين», «الألياف» (checked when `unmet_minimums` does not list protein/fiber), «بدون تكرار مع أمس» (always checked: a server rule). A small line «CP-SAT · <solver_status> · <solve_seconds> ث».
  4. «نبني أيام الأسبوع»: seven day chips that turn green on success, amber on a failed date, with the day's planned kcal under each.
  Then a summary «خطتك جاهزة» with «ابدأ يومك» -> `/today`. If some dates failed: «بنينا X من 7 أيام» and «حاول مرة أخرى للأيام الباقية».
- All animation off with `MediaQuery.disableAnimations` (steps still update, no reels). Live region semantics for step changes.
