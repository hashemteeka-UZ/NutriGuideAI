## 2. Learned bonus (#291)
- For the user's candidate meals (after Layer 1), call the L.1 `LearnedScorer` (replay cache) and map each UCB to an integer bonus in [0, 60] objective units (60 tenths = 6 kcal-equivalent, i.e. about 2 kcal of calorie deviation at W_KCAL = 3; verify this arithmetic against the module docstring and report it); set `MAX_LEARNED_BONUS = 60` in app/ml/config.py and document the mapping (clip UCB to [-1, 1], linear to [0, 60]).
- Objective: `tenths − liked_bonus − Σ learned_bonus_i·x_i + Σ variety_penalty_i·x_i` with correct variable bounds. Keep LIKED_BONUS as is (it is ingredient based, separate from the model).
- Tests: with bonuses the solution still satisfies `_verify`; a meal with a large bonus is chosen over an equal-cost one; the bonus cannot push the kcal deviation outside the band (constraint); empty mappings = identical objective and choices to cpsat_v1 on the existing optimizer fixtures.

## 3. Weekly variety (#292)
- Keep the existing exclusion of yesterday's meals. Add a soft penalty for meals planned on days D−2 … D−6: penalty = round(40 × (7 − age) / 5) objective units (age 2 -> 40, age 6 -> 8), summed if a meal appears more than once. Constants in optimizer config with a comment.
- Test: a fixture where cpsat_v1 alternates two menus now uses more distinct meals across 7 days while all days stay feasible.

## 4. Swap ordering (#293)
- Alternatives that pass the existing swap checks are ordered by the learned MEAN (no exploration term) descending, then by the current kcal-closeness rule; keep the limit of 10. With no user events the order equals today's order (test).
