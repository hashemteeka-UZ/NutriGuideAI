## 4. Profile service `app/services/profile.py` (#136, #176 to #178)
Public API (no FastAPI imports):
- `ProfileInput` (frozen dataclass mirroring `ProfileUpdate`, codes as strings).
- `save_profile(session, user_id, data: ProfileInput, now) -> ProfileOutcome` and `load_profile(session, user_id, now) -> ProfileOutcome`, where `ProfileOutcome` holds the profile row, its four child sets as codes/ids, the latest weight `(date, kg)` or `None`, the `ScreeningResult`, and the current `UserTarget` or `None`. `load_profile` raises `ProfileNotFoundError` when there is no profile.

`save_profile`, all in the caller's transaction, in this order:
1. `zone(data.timezone)` (raises `InvalidTimezoneError`). The user's local date `today` uses the NEW timezone.
2. Resolve every condition, allergen and cuisine code and every ingredient id in one query per table. Any unknown one → new `UnknownCodeError(kind, values)` (`ValueError` subclass) mapped to `422 UNKNOWN_CODE`; the detail names the kind and the unknown values. Codes are case-sensitive.
3. First save (no profile row) and `current_weight_kg` is null → `MissingWeightError` (`409 NO_WEIGHT`). Nothing is written.
4. Upsert the `user_profiles` row (all fields, including `water_goal_ml` where null clears it).
5. Replace the four child sets by difference (#176): delete rows not in the request, update changed `severity`/`stance` in place, insert new ones. Unchanged rows keep their `created_at`/`updated_at`. `diagnosed` stays at its default.
6. Weight (#178): when `current_weight_kg` is given, write it as the weight of `today` with `updated_at = now` through a new public `upsert_weight(session, user_id, measured_on, weight_kg, updated_at, now) -> (WeightLog, WeightStatus)` extracted from `weight._upsert` + `_weight` validation. `record_weight` keeps using it and behaves exactly as before. The profile service does NOT call `record_weight`, so one save makes at most one target.
7. Goal direction (#177): before any target work, validate the goal against the latest weight with a new public `validate_goal(goal_type, target_weight_kg, weekly_rate_kg, weight_kg)` extracted from `targets._validate` (same messages; `_validate` calls it). A failure raises `TargetValidationError` (`422 TARGET_VALIDATION`) and the whole save rolls back. This runs even when screening fails, so an invalid goal is never stored.
8. Screening `screen_user(session, user_id, today)`.
9. Target (#177), at most one per save:
   - Ineligible: no new target; if a current target exists, close it (`valid_to = now`) so no stale target can feed the planner. Response `target: null`.
   - Eligible, no current target: `INITIAL` if the user never had any `user_targets` row, otherwise `PROFILE_CHANGE` (returning from ineligible).
   - Eligible with a current target, first match wins: `GOAL_CHANGE` if `goal_type`, `target_weight_kg` or `weekly_rate_kg` changed; `PROFILE_CHANGE` if `sex`, `birth_date`, `height_cm` or `activity_level` changed; `WEIGHT_UPDATE` if the latest weight differs from the current target's `based_on_weight_kg` by at least `WEIGHT_RECOMPUTE_DELTA_KG`; otherwise keep the current target.
   - Create through `create_user_target(session, user_id, reason, now)` (unchanged).
   - Conditions, allergens, ingredient prefs, cuisines, wake/sleep times, timezone and water goal never create a target (targets_v1 does not use them).
10. Return the outcome. The router commits.
