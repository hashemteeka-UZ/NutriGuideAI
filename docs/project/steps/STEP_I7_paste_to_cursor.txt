## 3. Batch service `app/services/sync_batch.py` (#208, #209)
- `apply_batch(session, user_id, operations, now) -> list[OpOutcome]`, where `OpOutcome` holds `op_id`, `status` (`CREATED`, `UPDATED`, `DUPLICATE`, `REJECTED`), `entity_id`, and, when rejected, the caught exception.
- Operations run in the given order, each inside `session.begin_nested()`, through the SAME request-layer functions the single routes use (`logging_requests`, `water.log_water/delete_water`, `weight.record_weight`, `interactions.record_interaction`). No rule is copied.
- An exception that the router's error table knows (the `SERVICE_ERRORS` classes, including `InputRejectedError`) rolls back that savepoint only, and the operation is `REJECTED`. Anything else propagates: the router returns 500 and nothing of the batch is committed (retrying is safe because every operation is idempotent).
- Idempotent outcomes (#209): create with a known `client_uuid` and same content → `DUPLICATE`; correction with a known `new_client_uuid` and same content → `DUPLICATE`; deleting a log the same user already deleted → `DUPLICATE` (another user's or unknown id stays `LOG_NOT_FOUND`); a weight with an older `updated_at` (`STALE_IGNORED`) → `DUPLICATE`; a weight that replaced a value → `UPDATED`.
- `entity_id`: the log, water log, interaction id, or null for weights.
- Router `POST /sync/batch`: rate limit `SYNC_RATE_LIMIT` (per user key). It maps each rejected exception to its code with the same table used for problem responses (one shared lookup function in `app/api/errors.py`, not a copy), commits once, returns `SyncResult` with `server_time = now`.
- A plan-item log in the batch writes ACCEPT exactly as the single route does.

`changes_since(session, user_id, since, now, lang)`:

- `server_time = now`. The app sends it back as the next `since`.
