## 2. Plan view service `app/services/plan_view.py` (#190)
One function builds the response data of a stored plan, used by every route that returns a plan or plan item:
- `plan_view(session, user_id, plan, lang) -> PlanViewData`: target from `plan.target_snapshot["target"]` (never from the current target); items ordered BREAKFAST, LUNCH, SNACK(s), DINNER then id; each item: meal summary through `meal_catalog` (batched, same name and stance rules), `servings_multiplier`, `grams = serving_grams * multiplier`, `kcal/protein_g/carb_g/fat_g` = stored per-serving values × multiplier, `reason_codes`, `was_swapped`, `logged = has_active_log`.
- `totals`: sum over items of the eight `NutrientTotals` nutrients from `meal_nutrients` × multiplier. If any item lacks a nutrient, that total is `null`, never a partial sum (§9.8).
- `kcal_within_10pct`: `abs(totals.kcal - target.kcal) <= 0.10 * target.kcal`; false when `totals.kcal` is null.
- `unmet_minimums`: `planner.unmet_minimums(totals, limits)` with the limits rebuilt from `plan.target_snapshot["limits"]`. Add `ResolvedLimits.from_snapshot(...)` next to `to_snapshot` (additive) with a round-trip test.
- `stats`: only for `cpsat` plans, from `target_snapshot["solver"]`: `solver_status`, `kcal_relaxed`, `solve_seconds`, `candidate_meals`. `null` for greedy plans and for older cpsat plans whose snapshot lacks the two new keys.
- For the two new keys (additive, #191): `OptimizedDay` gets `candidate_meals: int` (distinct meal ids that passed Layer 1 for at least one position), and `create_day_plan` adds `solve_seconds` (rounded to 3 places) and `candidate_meals` to the `solver` dict it already stores. Nothing else in the snapshot changes. Confirm the reports and their tests are unchanged.
- Queries: a fixed number per plan regardless of item count (test it like I.4).

## 4. `GET /plans` and `GET /days/{date}` (#134, #193)
- `GET /plans?date_from&date_to` (max 31 days, already in the schema): the current plan of each day that has one (`current_plan_id`), ordered by date, each through `plan_view`.
- `GET /days/{date}`: `PROFILE_NOT_FOUND` without a profile. Returns:
  - `plan`: the current plan of that day or `null`.
  - `meal_windows` (#193), new pure function `meal_windows(wake_time, sleep_time) -> list[MealWindow]` in `app/services/meal_windows.py`. Awake span D = sleep − wake in hours, wrapping past midnight. Reference day D = 16 h (wake 07:00, sleep 23:00). Breakfast [wake + 0:30, wake + 2:30]. Lunch [wake + 6 h·k, wake + 8 h·k] and snack [wake + 9.5 h·k, wake + 10.5 h·k] with k = D / 16. Dinner [sleep − 4:30, sleep − 2:30]. Times are local clock times modulo 24 h, rounded to 5 minutes. If D < 10 h, return `[]` (no sensible schedule). Order BREAKFAST, LUNCH, SNACK, DINNER. Tests: 07:00/23:00 gives 07:30–09:30, 13:00–15:00, 16:30–17:30, 18:30–20:30; a late sleeper 10:00/02:00; D < 10 h gives `[]`.
  - `adherence`: `daily_adherence(session, user_id, date)` mapped to `DayAdherenceOut`.
  - `water`: new read function `water_day(session, user_id, day) -> (total_ml, goal, logs)` in `water.py`: active (`deleted_at IS NULL`) logs of that local date ordered by `consumed_at`, their sum, and `water_goal(...)` from I.3. Writing water stays for I.6.
