## 1. `app/services/consumption.py` — logging (§11.9, §33.4)

Shared rules:
- `log_date` = the local date of `consumed_at` in `user_profiles.timezone` (zoneinfo). An unknown timezone raises `InvalidTimezoneError`.
- `created_at = now` (server receive time). `client_uuid` is required by these services (F.1-d decision: every log behaves like a synced device log).
- **Idempotency by `client_uuid`** (F.1-d decision): if a row with that `client_uuid` already exists and its user, target (`meal_id`/`food_id`/`plan_item_id`), amount, `consumed_at` and `slot` are identical, return it with status `DUPLICATE` and write nothing; if any of these differ, raise `ClientUuidConflictError`. Otherwise status `CREATED`. Return a small result dataclass `(log, status)`.
- **`nutrients_snapshot`** (§11.9): JSON object `{"computation_version": "calc_v1", "nutrients": {<nutrient code>: "<exact Decimal string>", ...}}` with one key for **every** mandatory nutrient (`nutrients.is_mandatory`, §9.7), nothing else.
  - Meal: `amount_per_serving × servings_consumed` from the current `meal_nutrients`. If the meal is not nutritionally complete (`is_meal_nutritionally_complete`), raise `IncompleteNutritionError` (F.1-d decision: missing ≠ zero, §9.8, so a log never stores a guessed zero).
  - Food: `food_nutrients.amount × grams_consumed / 100`. A food missing any mandatory nutrient raises `IncompleteNutritionError` (same reason; every slice food passes G1, so this is only reachable in tests).
  - The snapshot is computed once at log time and never rewritten (a later recompute of the meal must not change it).

Services:
- `log_plan_item(session, user_id, plan_item_id, servings_consumed, consumed_at, client_uuid, now)`: the plan item must belong to a plan of this user (else `PlanItemNotFoundError`); `meal_id` = the plan item's `meal_id`, `slot` = the plan item's slot; `servings_consumed > 0` (partial or more than the planned multiplier are both allowed, e.g. 0.75 of a 1.5 item). A plan item that already has an **active** log raises `PlanItemAlreadyLoggedError` (F.1-d decision: one active log per plan item; a correction goes through `correct_log`).
- `log_meal(session, user_id, meal_id, servings_consumed, consumed_at, slot, client_uuid, now)`: off-plan catalog meal; `plan_item_id = NULL`; `slot` optional; inactive meals are allowed (the user ate it; F.1-d decision).
- `log_food(session, user_id, food_id, grams_consumed, consumed_at, slot, client_uuid, now)`: off-catalog food; `grams_consumed > 0`.
- `correct_log(session, user_id, log_id, *, servings_consumed=None, grams_consumed=None, consumed_at=None, slot=None, new_client_uuid, now)`: in one transaction, tombstone the old row (`deleted_at = now`, server time, §33.4 #72) and insert a new row that copies the old target (`plan_item_id`, `meal_id` or `food_id`) with the given changes and a fresh snapshot. Changing the target (another meal or food) is not a correction: the caller deletes and logs again (F.1-d decision). The old row's other columns are **never updated** (immutable rows, §11.9).
- `delete_log(session, user_id, log_id, now)`: tombstone only. Tombstoning a row that is already tombstoned, or a row of another user, raises `LogNotFoundError`.
- `active_logs(session, user_id, log_date)`: rows with `deleted_at IS NULL`, ordered by `consumed_at`, then `id`.

## 2. `app/services/plan_swap.py` — swapping a plan item (§11.8, §11.9 application rule)

`swap_plan_item(session, user_id, plan_item_id, new_meal_id, now) -> MealPlanItem`:
- Refuse (`PlanItemAlreadyLoggedError`) if the item has an active log, because that log points at the old meal.
- Re-resolve the user's condition limits with the plan's frozen `target_snapshot` kcal (`resolve_condition_limits`), load the user's preferences, and require the new meal to pass every Layer 1 rule for the item's slot at the item's multiplier (`evaluate_meal`); otherwise raise `SwapRejectedError(exclusion_codes)`.
- Within the plan day: no repeated meal and no second meal of the same `variant_group`; the day totals after the swap must stay within every resolved `max_per_day`; limit-tag servings must stay within their numbers. Reuse the planner's helpers; do not copy their logic.
- Update `meal_id`, set `was_swapped = true`, recompute `reason_codes` with the planner's function, set `updated_at = now`. The plan's `target_snapshot` is not changed.

## 3. `app/services/adherence.py` — daily adherence (§30.5)

`daily_adherence(session, user_id, log_date) -> DayAdherence` (frozen dataclass, read-only):
- Totals: sum of the active logs' `nutrients_snapshot` values for that `log_date`, per mandatory nutrient (exact Decimals).
- Target: the `user_targets` row valid on that date (§30.5 #72: the latest row whose `valid_from` is before the end of that local day in the user's timezone). No such row → `status = None`, reason `NO_TARGET`.
- Limits: `resolve_condition_limits` for the user's current conditions with that target's kcal (F.1-d decision: condition history is not stored, so past days use the current conditions; note it in the docstring).
- Status: `ACHIEVED` if energy within ±10% of `target_kcal` **and** no resolved `max_per_day` is exceeded; `PARTIAL` if energy within ±25%; otherwise `NOT_ACHIEVED`. A day with no active log is `NOT_ACHIEVED` with zero totals. Boundaries are inclusive (exactly 10% is within). Also return `exceeded_max_per_day` (nutrient code, total, limit) and `unmet_minimums` (information only, not part of the status, §30.4b) and `fiber_target_g` with the day's fiber (information only).
- Plan completion: the **current** plan covering that day (§11.7 #72: newest `created_at`, ties broken by larger `plan_id`, as F.1-c did); items of that day (`day_index = log_date − date_from`); consumed = items with at least one active log; `completion = consumed / total` as a Decimal rounded to 3 places; `None` if no plan covers the day. Water does not affect anything here.
- `adherence_range(session, user_id, date_from, date_to)` returns the list per day and the current streak of consecutive `ACHIEVED` days ending at `date_to` (§30.5: streaks are derived, never stored).

## 4. `app/services/weight.py` — weight log and recompute trigger (§11.10, §30.6)

Constants (F.1-d decisions): `CLOCK_SKEW_TOLERANCE = timedelta(minutes=5)`; `WEIGHT_RECOMPUTE_DELTA_KG = Decimal("1")` (§30.6); `GOAL_REACHED_DELTA_KG = Decimal("1")` (§30.3).

`record_weight(session, user_id, measured_on, weight_kg, updated_at, now) -> WeightResult`:
- `updated_at` (device time) must not be later than `now + CLOCK_SKEW_TOLERANCE` (else `ClockSkewError`); `weight_kg` range is enforced by the CHECK, but validate first and raise `ValueError` with a clear message.
- Upsert on `(user_id, measured_on)` (§11.10): no row → insert (`source = 'MANUAL'`, `created_at = now`); existing row with older `updated_at` → update `weight_kg` and `updated_at`; existing row with equal or newer `updated_at` → keep it and report `STALE_IGNORED` (last-write-wins, §33.4). Statuses: `CREATED`, `UPDATED`, `STALE_IGNORED`.
- Recompute trigger (§30.6): only if the written row is now the user's **latest** `measured_on`, the user has a current target, and `|weight_kg − based_on_weight_kg| ≥ 1 kg`: call `create_user_target(session, user_id, "WEIGHT_UPDATE", now)`. A back-dated weight that is not the latest never triggers. If the user has no current target, nothing is created (onboarding owns `INITIAL`; F.1-d decision). If screening now fails (for example the user turned pregnant), `create_user_target` raises; catch it, keep the weight row, and report `target_status = "INELIGIBLE"` (the old target stays; F.1-d decision, note it as a finding for §30.1).
- Result also carries `new_target_id` (or None) and `goal_reached: bool` (latest weight within ±1 kg of `user_profiles.target_weight_kg`, when that is set; information only, nothing is written, §30.3).
